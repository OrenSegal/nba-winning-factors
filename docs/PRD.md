# PRD: NBA winning factors

No product requirements document existed for this project; this one was written on 2026-11-07 from the README, the code and the cleanup history. Edit it if the intent was different.

## Problem
"What wins NBA games?" is usually answered with a leaky model (same-game box score predicting the same game) that reports 95%+ accuracy and teaches nothing. Answer it honestly: what is knowable before tipoff, and what only explains a game afterward.

## Users
A hiring manager, collaborator or reader of the repo who wants to see sound data-science practice on a familiar domain, and can reproduce it in minutes.

## Goals
1. Quantify pre-game predictive signal (accuracy, log loss, calibration) against honest baselines, with uncertainty.
2. Rank the four factors and rest effects, before the game (coefficients) and after it (margin attribution), and keep the two clearly separate.
3. Reproduce from a clean clone with one command each for install, test and run; deterministic outputs.
4. State limits plainly: where models do not beat a trivial rule, and where the data regime shifted.
5. Explain a season, not just a game: test every available factor family (shot diet, shot making, drives, passing, rebounding, defence, hustle) against winning at team-season level, separate style from execution, and make the full list explorable and downloadable.

## Non-goals
- A live prediction service, API or dashboard. The first version had one and it never worked; no one is waiting on it. Revisit only if a consumer exists.
- Betting-market comparison, player-level or injury data, hyperparameter search.
- A pipeline orchestrator, feature store or database. The data is 8.5 MB of CSV and the run takes minutes.

## Data architecture
| Layer | Where | Rule |
|---|---|---|
| Raw | `data/raw/gamelog_<season>.csv` | Immutable snapshot from `scripts/fetch_data.py`; committed; incremental fetch (skips seasons on disk). |
| Validated | `nbawin/data.py` `load_team_logs` | Schema and integrity checks on every load; fail loudly. |
| Game table | `to_games` | One row per game, neutral-site games dropped. Rebuilt in memory each run (seconds), not persisted: persisting would add a stale-cache failure mode for no speed gain. |
| Features | `nbawin/features.py` | Pre-game features use only earlier games (shift before expanding mean); same-game factors live in a separate function and never reach the predictive models. |
| Team-season | `data/raw/teamseason_<season>.csv`, `nbawin/style.py` | One row per team-season from `scripts/fetch_teamseason.py` (advanced, shot zones, tracking from 2013-14, hustle from 2016-17). Describes a finished season; never feeds the pre-game models. Metrics are z-scored within season. |
| Outputs | `results/` | `metrics.json` (all numbers), `report.md`, figures. Regenerated by `python -m nbawin.run`. |

## Evaluation design
- Fixed time split: train 2000-01 to 2022-23, test 2023-24 to 2025-26.
- Walk-forward backtest: each season from 2005-06 scored by models trained on earlier seasons only.
- Baselines: home wins, better record wins, win%-only logistic. Paired bootstrap for differences.
- Metrics: accuracy, log loss, Brier, ECE, calibration plot.

## Success criteria
- `uv sync --locked && uv run pytest && uv run python -m nbawin.run` works on a clean clone; two runs give byte-identical `metrics.json`.
- Leakage tests pass (own and future games cannot move a game's features).
- README claims match `results/report.md`.

## Known weaknesses / next experiments
- Home-court advantage fell from about 60% to about 55%; try a rolling or recency-weighted training window.
- The style/execution split in the team-season atlas rests on hand-assigned roles (see docs/decisions.md); a data-driven split (for example by partial correlation with shot outcomes) would be more defensible.
- Elo (cross-season carry-over) is implemented in `nbawin/factors.py` and beats season-to-date ratings in the opening weeks; a market-implied baseline (closing lines) is the next benchmark, subject to the data licence.
- Evaluation: bootstrap resamples games as independent (resample by date or week); the model comparison is not multiplicity-corrected beyond the factor screen.
- CIs treat games as independent.
